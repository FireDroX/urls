## Projet

**url.addrien.fr** — outil perso qui regroupe trois usages derrière un seul compte admin : raccourcir des URL (`/r/<id>`), partager des fichiers (`/d/<id>`) et en recevoir (`/u/<id>`). Même architecture que NestWiki (`../wiki`, à consulter pour tout pattern déjà résolu là-bas) : pnpm workspace avec `backend/` (NestJS + TypeORM + MySQL 8) et `frontend/` (React + TypeScript + Vite, TailwindCSS + shadcn/ui).

Le plan de référence est `Plan url.addrien.fr.md` (phases 0 à 4, exigences de sécurité transverses) et la maquette `Maquette url.addrien.fr.html` (thème sombre, Montserrat / Noto Sans, accent orange) ; les deux restent hors dépôt (`.gitignore`). Une fonctionnalité n'est terminée qu'avec ses limites, ses codes d'erreur et ses contrôles d'intégrité.

État : phases 1 (redirections `/r/`) et 2 (partages `/d/`, fichiers stockés) livrées. **Phase 3** en cours (dépôts `/u/`) : colonnes et API admin des dépôts (`/api/drops`) en place ; page publique d'envoi à venir.

## Commandes

Toujours lancer l'app via les scripts `pnpm run <script>` du package concerné. Ports de dev : backend `:3001`, frontend `:5174` (NestWiki occupe déjà `:3000`/`:5173`) ; vérifier les ports avant de lancer un serveur, et arrêter ceux qu'on a lancés (`netstat -ano | grep ":3001"`, puis `taskkill //F //PID <pid>`).

```bash
cd backend && pnpm run start:dev    # API en watch (http://localhost:3001/api)
cd frontend && pnpm run dev         # Vite, proxifie /api et /r/ vers VITE_API_PROXY_TARGET
```

Backend (`backend/`) :

```bash
pnpm run lint                # eslint --fix
pnpm run test                # vitest
pnpm run build
pnpm run migration:run       # applique les migrations TypeORM en attente
pnpm run migration:revert    # annule la dernière migration
pnpm run migration:generate  # diff entities vs DB — à relire, jamais pris tel quel
pnpm run seed:admin          # crée le compte admin depuis ADMIN_* si la base n'a aucun compte (idempotent, lancé par entrypoint.sh ; Nest refait la même vérification au démarrage)
```

Frontend (`frontend/`) : `pnpm run lint` (oxlint), `pnpm run test` (vitest + jsdom), `pnpm run build`.

## Environnement

Dev : la base et le S3 tournent sur la VM docker de dev `192.168.2.64` (stack `/opt/nestwiki-dev` : MySQL 8.4 sur `:3306`, RustFS sur `:9000`), partagés avec NestWiki : base `urls`, utilisateur MySQL `urls` limité à `urls.*`, bucket `urls` et utilisateur S3 `urls` limité à ce bucket. `infra/rustfs/setup.sh` (local, **hors dépôt** : `infra/` est dans `.gitignore`) crée bucket, utilisateur, politique, quota et CORS (le CORS du bucket ne sert plus à l'upload, qui passe par le backend ; idempotent, avec le compte admin RustFS — jamais celui de l'app).

Config : trois `.env`, chacun avec un `.env.example` à copier.

- racine — lu par `docker compose` uniquement (mots de passe MySQL/RustFS du compose complet, réseaux externes de prod, `VITE_TURNSTILE_SITE_KEY` pour le build de l'image frontend).
- `backend/.env` — `PUBLIC_URL` (origine publique : CORS, cookies `Secure` si `https://`), `DB_*`, `JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET`, `IP_HASH_SECRET` (clé HMAC des IP des visiteurs, 32 caractères min.), `ADMIN_EMAIL`/`ADMIN_PASSWORD`, `S3_ENDPOINT` (accès interne), `S3_PUBLIC_ENDPOINT` (hôte public qui **signe** les URLs présignées — `https://cdn.addrien.fr` en prod, la signature couvre l'hôte), `S3_ACCESS_KEY`/`S3_SECRET_KEY`/`S3_BUCKET`/`S3_REGION`, `TURNSTILE_SECRET_KEY`, `CLIENT_IP_HEADER` (`cf-connecting-ip` derrière le tunnel) et `TRUST_PROXY_HOPS`. **`validateEnvironment` (`src/config/env.validation.ts`) bloque le démarrage** si un secret est absent, trop court ou une valeur par défaut connue (`KNOWN_DEFAULT_SECRETS`), si les deux secrets JWT sont identiques, ou si `TURNSTILE_SECRET_KEY` manque alors que `PUBLIC_URL` est en `https://` — sauf `DEV=true` (dev local uniquement, jamais en prod).
- `frontend/.env` — `VITE_API_URL` (`/api` : même origine, nginx en prod et le proxy Vite en dev), `VITE_API_PROXY_TARGET`, `VITE_TURNSTILE_SITE_KEY`.

Ne jamais afficher ni copier les valeurs des `.env` : générer de nouveaux secrets (`openssl rand -hex 32`).

## Déploiement

- `docker-compose.yml` : stack complète (mariadb + rustfs + backend + frontend, plus `storage-init` en profil `setup`, qui monte `infra/rustfs`), pour un serveur vierge ou un essai local. Réseaux `database` et `storage` en `internal`, partagés seulement avec le backend ; seul le frontend publie un port (`127.0.0.1:8081`), servi par le Cloudflare Tunnel.
- `docker-compose.external.yml` : prod, la base et le RustFS existent déjà (ceux de NestWiki, S3 exposé sur `cdn.addrien.fr`). La base de prod est un `mariadb:11` (comme `docker-compose.yml`), celle de la VM de dev un MySQL 8.4 : les migrations doivent passer sur les deux (`DROP CONSTRAINT`, jamais `DROP CHECK`, contrôlé par `migrations-portability.spec.ts`). Images `ghcr.io/firedrox/urls-{backend,frontend}` poussées par la CI sur `main`, réseaux externes `DATABASE_NETWORK`/`STORAGE_NETWORK` (réseaux `--internal` dédiés).
- Backend : utilisateur `node` (non root), `mem_limit`, `read_only`, `no-new-privileges`. `entrypoint.sh` lance migrations, seed admin puis l'API. Le frontend nginx proxifie `/api/` et `/r/` vers `backend:3000` (la route des parts d'upload a sa propre `location` : `client_max_body_size 33m`, `proxy_request_buffering off`, le reste de `/api/` garde la limite de 1 Mo) et envoie la CSP (scripts du site + Turnstile seulement), `nosniff`, `X-Frame-Options`.

## Architecture backend (`backend/src`)

NestJS, un module par domaine directement sous `src/` (pas de dossier `modules/`) : `audit`, `auth`, `drops`, `events`, `files`, `health`, `links`, `security`, `settings`, `shares`, `storage`, `users`, plus `common/` (filtres, DTOs, exceptions, guards, décorateurs, stratégie JWT, constantes), `config/` (TypeORM, validation de l'environnement) et `database/` (migrations, seed admin). Pour créer un module : skill `new-backend-module`.

Même découpage en couches que NestWiki :

- `<module>.controller.ts` — HTTP uniquement : un appel au service, puis le mapper construit la réponse. Routes protégées par `@UseGuards(JwtAuthGuard)` (un seul compte : pas de rôles) ; toujours `@UseFilters(<Module>ExceptionFilter)`.
- `services/*.service.ts` — logique métier **et validation**. Pas de `class-validator` ni de `ValidationPipe` : le controller reçoit `@Body() body: unknown`, le service le passe à `parseDto(<schema>, body)` (`common/parse-dto.ts`), qui lève `ValidationException` (400). Lève des exceptions de domaine depuis `common/exceptions/<domaine>/*.exception.ts` (`extends Error`, `this.name = '<NomDeClasse>'`).
- `dto/in/*.dto.ts` — un schéma `zod` (`z.strictObject`, longueurs max, normalisation) et le type inféré. `dto/out/*.dto.ts` — une `interface`, enveloppée dans `ResponseDto<T>`.
- `entities/*.entity.ts` — entités TypeORM ; le schéma appartient aux migrations SQL brutes (`src/database/migrations/`, `queryRunner.query`), **jamais** `synchronize: true`. Noms explicites pour index et clés étrangères.
- `persistence/` — port (interface) + adapter `typeorm.*.repository.ts`, injecté via un **token string littéral** au pluriel (`'UsersRepository'`, `'AuditLogsRepository'`) : il doit différer de `` `${EntityName}Repository` ``, déjà enregistré par `@nestjs/typeorm`.
- `mapper/*.mapper.ts` — classe statique entity → DTO qui construit le `ResponseDto`.
- `filter/*.exception.filter.ts` — `@Catch()` par module, table `exception.name` → statut ; un nom inconnu part dans `HttpExceptionFilter.respond`.

**Erreurs** : format unique `{ error: '<message>' }` (messages en anglais). `common/filters/http-exception.filter.ts` (aussi filtre global) garde le vrai statut des `HttpException` et des erreurs body-parser exposées (400, 413…), et répond `500 Internal server error` sans jamais exposer le message interne (SQL, stack), qu'il logge. Jamais de 500 pour une erreur client : chaque exception de domaine doit être mappée dans le filtre de son module (et ceux des modules qui l'appellent).

**`common/variables.global.ts`** centralise les constantes (longueurs, durées, limites de débit, alphabet des IDs publics…) : y ajouter les nouvelles.

**IDs publics** : `generatePublicId()` (`common/public-id.ts`, nanoid base62, 8 caractères). Ne jamais exposer un ID SQL (uuid interne) dans une réponse ou une URL.

**Auth** : un seul compte, créé depuis `ADMIN_*` (`database/default-admin.ts`). Mot de passe hashé en argon2id (`common/password.ts`, `@node-rs/argon2`). JWT access 15 min + refresh 7 j en cookies `httpOnly`, `SameSite=Strict`, `Secure` si `PUBLIC_URL` est en `https://`. `JwtStrategy` → `SessionUserResolver` recharge l'utilisateur à chaque requête et refuse un jeton antérieur au dernier changement de mot de passe (qui déconnecte donc les autres sessions). Verrouillage après `MAX_FAILED_LOGIN_ATTEMPTS` échecs (423 + `Retry-After`), compteur remis à zéro à l'expiration. Turnstile vérifié côté serveur (`security/services/turnstile.service.ts`) avec l'IP cliente réelle.

**IP cliente et rate limits** : `resolveClientIp` (`common/client-ip.ts`) lit `CLIENT_IP_HEADER` (`cf-connecting-ip` en prod) sinon `req.ip`, calculé par Express avec `trust proxy = TRUST_PROXY_HOPS`. `ThrottlerBehindProxyGuard` (global, 100 req/min) l'utilise ; `@Throttle` plus strict sur l'auth. Le throttler répond 429 avec `Retry-After`, affiché par le front (`lib/api-errors.ts`).

**Audit** : `AuditLogService.record` (`audit/`) journalise connexions (réussies, échouées, verrouillées), changements de mot de passe et de réglages, et créations, modifications et suppressions de liens (`AuditAction`).

**Liens** (`links/`) : une seule table `links` pour les trois types (`redirect`, puis `share` et `drop`), contrainte `CHECK` sur le type et sur la destination obligatoire d'une redirection. `public_id` = slug choisi ou `generatePublicId()`, unique et en `utf8mb4_bin` (sensible à la casse, comme l'alphabet base62). API admin `GET/POST /api/links`, `GET/PATCH/DELETE /api/links/:id` (`:id` = `public_id`) ; tout est modifiable (destination, slug, expiration, désactivation). Suppression en soft delete (`deleted_at`) : le slug d'un lien supprimé reste pris (409), pour qu'une ancienne URL partagée ne pointe jamais vers une autre destination. Limites (longueurs, alphabet du slug, noms réservés, throttle de création) dans `variables.global.ts`.

**Redirection publique `/r/:id`** (`links/redirects.controller.ts`) : seule route hors du préfixe `/api` (`exclude` de `setGlobalPrefix` dans `main.ts`), servie par le backend pour répondre côté serveur. Lien actif → `302` vers la destination, `Cache-Control: no-store` (jamais de 301 ni de cache). Lien inexistant, désactivé, supprimé ou id mal formé (vérifié avant toute requête SQL) → même `LinkNotFoundException` (404, corps et en-têtes identiques) ; `expires_at` passé → `LinkExpiredException` (410). `@Throttle` dédié (`LINK_REDIRECT_THROTTLE_*`, par IP via `resolveClientIp`). Les pages 404/410 sont celles de la SPA, statut conservé : nginx (`proxy_intercept_errors` + `error_page 404 410 /index.html`) et le proxy Vite (plugin `public-link-proxy` de `vite.config.ts`) remplacent le corps JSON par `index.html` ; la route `/r/:id` du front (`RedirectUnavailable`) relit le statut par un `fetch` sans suivre la redirection (`redirect: 'manual'`) et affiche « lien introuvable » ou « lien expiré » dans la langue du site. Les 429 passent tels quels (`Retry-After` conservé).

**Événements** (`events/`, port `'EventsRepository'`, entité `LinkEvent`) : table `events` (`link_id` → `links.id` en `ON DELETE CASCADE`, `type` contraint par `CHECK`, index `(link_id, created_at)` pour les stats). Un `302` de `/r/:id` appelle `EventsService.recordClick` sans l'attendre (les 404/410/429 n'enregistrent rien) ; le décorateur `@CurrentVisitor()` (`common/visitor.ts`) fournit l'IP (`resolveClientIp`), `Referer`, `User-Agent` et `CF-IPCountry`. Referer et user-agent tronqués (`EVENT_*_MAX_LENGTH`), pays gardé seulement s'il fait 2 lettres (`XX`, `T1` → `null`), IP stockée uniquement en HMAC-SHA-256 hex avec `IP_HASH_SECRET` : jamais en clair, ni en base ni dans les logs. Un échec d'insertion est loggé, la redirection part quand même. Stats : `GET /api/links/:id/stats?days=N` (`LinksService.stats` valide `days` par `linkStatsQuerySchema` : entier de `LINK_STATS_MIN_DAYS` à `LINK_STATS_MAX_DAYS`, `LINK_STATS_DEFAULT_DAYS` par défaut, tout autre paramètre → 400 ; lien inconnu ou supprimé → 404), agrégée en SQL par l'adapter (`GROUP BY` sur l'index `(link_id, created_at)` : clics par jour, top `LINK_STATS_TOP_LIMIT` sources et pays, `null` = direct / pays inconnu). Les sources sont groupées par hôte : `referer_host`, rempli à l'insertion par `refererHost` (`common/referer-host.ts` : hôte en minuscules sans port, `null` si le referer est absent, invalide ou non http(s)), l'API renvoie `referers: [{ host, clicks }]` ; `EventsService.clickStats` complète les jours sans clic à 0. **Jours en UTC** (`created_at` est écrit en UTC : `timezone: 'Z'` côté pilote, et `config/mysql-connection.ts` envoie `SET time_zone = '+00:00'` sur chaque connexion du pool — app, migrations et seed partagent `mysqlConnectionOptions` —, pour les `CURRENT_TIMESTAMP` remplis par MySQL) : la fenêtre commence à minuit UTC il y a `N - 1` jours, aujourd'hui inclus, et la réponse porte `timeZone: 'UTC'`.

**Partages** (`shares/`, port `'SharesRepository'` sur l'entité `Link` limitée au type `share`) : API admin `GET/POST /api/shares`, `GET/PATCH/DELETE /api/shares/:id` (`:id` = `public_id`), mêmes règles de slug que les redirections (`slugSchema`, `expiresAtSchema` de `links/dto/in/link-fields.schema.ts`, id mal formé → 404 avant SQL via `isWellFormedLinkId` de `common/public-id.ts`, 409 si pris), `maxDownloads` facultatif (1 à `SHARE_MAX_DOWNLOADS_LIMIT`, `CHECK` en base : seulement pour un `share`), `downloadCount` en lecture seule, `SHARE_FILES_MAX` fichiers au plus par partage (appliqué à l'upload) ; tout est modifiable, soft delete, audit `shares.*`. La liste donne `fileCount`/`totalSize` par partage (agrégés en SQL), la fiche ajoute `files` (`publicId`, nom, taille, MIME, statut). **Fichiers** (`files/`, entité `StoredFile`, port `'FilesRepository'`, `FilesService` exporté) : table `files` (`link_id` → `links.id` en `ON DELETE RESTRICT` : un lien ne se supprime jamais en dur tant que des lignes de fichiers le référencent ; `s3_key` unique, `size` en `bigint` converti en nombre, `sha256` annoncé contrôlé par `CHECK`, `status` ∈ `FILE_STATUSES` (`uploading` → `verifying` → `ready` | `rejected`), `upload_id` multipart, soft delete). `isDuplicateEntry` (`common/database-errors.ts`) traduit `ER_DUP_ENTRY`.

**Upload multipart via le backend** (`shares/share-files.controller.ts` → `ShareFilesService` → `files/services/file-uploads.service.ts`, admin, `JwtAuthGuard`, filtre `ShareFilesExceptionFilter`) : le navigateur n'écrit jamais dans S3, il envoie ses parts au backend qui les transmet en flux à `UploadPart` par le client interne : pas d'URL d'upload présignée, pas de CORS sur le bucket, pas de CSP à élargir.

- `POST /api/shares/:id/files` (`{ name, size, sha256 }`, `files/dto/in/start-upload.dto.ts` : nom réduit à son nom de base, sans caractères de contrôle ni invisibles, 1 à `FILE_NAME_MAX_LENGTH` ; SHA-256 hex normalisé en minuscules) : `size` > `FILE_MAX_SIZE_BYTES` → 413 ; puis `CreateMultipartUpload` sous une clé opaque `files/<uuid>` et `insertWithinLimits` (adapter : transaction, `SELECT … FOR UPDATE` sur le lien, plus de `SHARE_FILES_MAX` fichiers → 413, somme SQL des tailles non rejetées ni supprimées + taille annoncée > `FILES_STORAGE_QUOTA_BYTES` → 413) ; un refus annule l'upload multipart. Réponse : `fileId`, `partSize` (`FILE_PART_SIZE_BYTES`, 32 Mio), `partCount`, `file`.
- `PUT …/files/:fileId/parts/:n` : `n` de 1 à `partCount` et `Content-Length` égal à la taille attendue de la part, `Transfer-Encoding` refusé (400) ; le corps (jamais en mémoire) passe par `measuredPart` (`files/file-streams.ts` : coupe en 413 au-delà, 400 si plus court ou client parti) puis `UploadPart`. Le parseur JSON ignore cette route (`common/json-body.ts`, option `type` de `useBodyParser` dans `main.ts`). `@Throttle` dédié (`FILE_PART_THROTTLE_LIMIT`). Une part se renvoie seule.
- `GET …/files/:fileId/parts` : reprise d'un upload. `ListParts` d'un fichier `uploading` : `fileId`, `size`, `sha256` annoncé, `partSize`, `partCount`, `parts: [{ partNumber, size }]` (ni clé S3, ni `upload_id`, ni ETag) ; fichier inconnu, d'un autre partage ou supprimé → 404, plus en `uploading` → 409.
- `POST …/files/:fileId/complete` : `ListParts` (nombre et taille de chaque part, sinon 409), `CompleteMultipartUpload` (« Bucket quota exceeded » → `StorageQuotaExceededException`, 413), passage conditionnel `uploading` → `verifying` (sinon 409 ; si la ligne a été supprimée entre-temps, l'objet est effacé et un nettoyage raté est loggé avec sa clé sans changer la réponse, l'objet d'un `complete` concurrent sur une ligne vivante n'est jamais touché), 202. `FileVerificationService` vérifie en tâche de fond (`HeadObject` pour la taille, SHA-256 recalculé en relisant l'objet en flux, MIME détecté par `file-type` sur les `FILE_MIME_SNIFF_BYTES` premiers octets, `application/octet-stream` à défaut) → `ready`, sinon `rejected` et objet supprimé ; une erreur de stockage laisse le fichier en `verifying`, repris au démarrage suivant (`onApplicationBootstrap`).
- `DELETE …/files/:fileId` : passe par `FileDeletionService.erase` (voir « Fichiers stockés »), 503 si le stockage est injoignable. Audit `files.created` / `files.deleted`.
- Fichier inconnu ou d'un autre partage → 404, plus en `uploading` (ou upload inconnu de S3, `NoSuchUpload`) → 409, stockage injoignable → 503. Le client S3 est réglé en `requestChecksumCalculation`/`responseChecksumValidation` `WHEN_REQUIRED` (`S3_CHECKSUM_MODE`) : pas d'encodage `aws-chunked` sur les parts envoyées en flux.

**Fichiers stockés** (`files/files.controller.ts` → `FilesAdminService`, admin, filtre `FilesExceptionFilter`) : `GET /api/files` liste les fichiers non supprimés, du plus récent au plus ancien, chacun avec `inUse` et son lien (`type`, `publicId`, `deleted`, `disabled`, `expired` via `isLinkUsedUp` de `common/link-expiry.ts`) ; `?orphans=true` (seule valeur admise, tout autre paramètre → 400) ne garde que les orphelins. Règle `isFileInUse` (`files/file-usage.ts`) : un fichier est utilisé si son lien est un `share` non supprimé, même désactivé ou expiré ; un fichier d'un partage supprimé ou d'un lien `drop` est orphelin. `summary` (toujours sur tous les fichiers) : `quotaUsedBytes` (même règle SQL que `insertWithinLimits`, `COUNTED_FILES`), `quotaLimitBytes` (`FILES_STORAGE_QUOTA_BYTES`), `orphanBytes` (orphelins hors `rejected`) et `storageUsedBytes` (usage réel de RustFS, `null` s'il est injoignable). `DELETE /api/files/:id` : id inconnu, mal formé ou supprimé → 404, fichier utilisé → 409, sinon `FileDeletionService.erase` (chemin unique, aussi utilisé par `DELETE /api/shares/:id/files/:fileId`) : `AbortMultipartUpload` si `uploading` (`NoSuchUpload` → `DeleteObject`), sinon `DeleteObject` (objet déjà absent = succès), **puis** soft delete de la ligne ; pour tout fichier lu en `uploading` (Abort réussi ou `NoSuchUpload`), un `DeleteObject` part **après** le soft delete et **avant** l'audit `files.deleted`, et sur le chemin `NoSuchUpload` un premier `DeleteObject` part aussi avant le soft delete (son échec donne 503, la ligne reste, un nouveau `DELETE` reprend ; un `complete` concurrent a pu aboutir malgré l'abandon : si son passage à `verifying` a précédé le soft delete, c'est ce `DeleteObject` qui efface l'objet, sinon `complete` le nettoie lui-même), au mieux : un échec est loggé avec la clé de l'objet et `erase` se termine quand même par son audit ; stockage injoignable → 503, la ligne reste et un nouveau `DELETE` reprend. `POST /api/files/:id/download` : fichier `ready` → `{ url }` présignée `FILE_DOWNLOAD_URL_TTL_SECONDS` en `attachment`, autre statut → 409, sans toucher à `download_count` ni aux événements.

**Page publique `/d/:id`** : route SPA (`pages/ShareDownload.tsx`, hors layout admin, servie par le `location /` de nginx) qui lit `GET /api/public/shares/:id` (`shares/public-shares.controller.ts` → `PublicSharesService`, sans session, `@Throttle` `SHARE_VIEW_THROTTLE_*`, `Cache-Control: no-store`) : fichiers `ready` seulement (`publicId`, nom, taille), nombre, taille totale, `expiresAt`. Id mal formé, inexistant, désactivé, supprimé ou sans fichier prêt → même `ShareNotFoundException` (404) ; expiré ou `download_count >= max_downloads` → `ShareExpiredException` (410). Un 200 appelle `EventsService.recordView` sans l'attendre. `POST /api/public/shares/:id/files/:fileId/download` (`{ turnstileToken }`, `@Throttle` `SHARE_DOWNLOAD_THROTTLE_*`) : Turnstile vérifié avec l'IP réelle avant toute lecture (400 sinon), puis `incrementDownloadCount` (un seul `UPDATE` gardé par `download_count < max_downloads`, expiration, désactivation et soft delete : la course sur le dernier téléchargement donne un seul gagnant, l'autre reçoit 410), `recordDownload`, et URL présignée `SHARE_DOWNLOAD_URL_TTL_SECONDS` signée par `S3_PUBLIC_ENDPOINT` en `attachment` avec le nom d'origine ; le front y navigue (`utils/start-download.ts`) et redemande un jeton Turnstile après chaque essai. `events.type` ∈ `EVENT_TYPES` (`click`, `view`, `download`) ; la fiche admin d'un partage ajoute `viewCount` (`EventsService.countViews`) à `downloadCount`.

**Dépôts** (`drops/`, port `'DropsRepository'` sur l'entité `Link` limitée au type `drop`) : API admin `GET/POST /api/drops`, `GET/PATCH/DELETE /api/drops/:id` (`:id` = `public_id`), mêmes règles de slug, d'expiration, de 404 avant SQL, de 409, de soft delete que les partages ; audit `drops.*`. Colonnes de `links` : `title` (facultatif, `DROP_TITLE_MAX_LENGTH`, sans caractère de contrôle), `max_total_bytes` (`bigint`, 1 à `FILES_STORAGE_QUOTA_BYTES`) et `max_files` (1 à `SHARE_FILES_MAX`, un dépôt tient donc toujours dans un partage) ; `CHECK` nommés `CHK_links_drop_max_total_bytes` / `CHK_links_drop_max_files` : obligatoires et > 0 pour un `drop`, `NULL` sinon. Le transformer `bigintToNumber` (`common/bigint-to-number.ts`) garde `null` à `null` : la colonne est `NULL` pour tous les autres types. Les deux limites sont obligatoires à la création, modifiables ensuite et peuvent descendre sous l'usage courant (le dépôt devient `full`, rien n'est supprimé). La liste et la fiche donnent `fileCount`/`totalSize` (agrégés en SQL par `summarizeCountedByLinkIds`, règle `COUNTED_FILES` : ni rejetés ni supprimés, contrairement à `summarizeByLinkIds` des partages) et `state` ∈ `DROP_STATES`, calculé par `dropState` (`common/drop-state.ts`, partagée avec l'envoi public) selon la précédence `disabled` > `expired` > `full` > `open` ; `full` dès que le nombre ou les octets atteignent la limite, ou si une limite est `null` (échec fermé). L'expiration passe par `isLinkExpired` (`common/link-expiry.ts`). Un `drop` n'est jamais servi par `/r/`, `/api/links` ni `/api/shares` (404).

**Stockage** : client AWS SDK v3 (`storage/`), `forcePathStyle`, deux clients : interne (`S3_ENDPOINT`) et de signature (`S3_PUBLIC_ENDPOINT`). Bucket privé, accès uniquement par URLs présignées en `Content-Disposition: attachment`. `GET /api/storage/usage` lit `GET /rustfs/admin/v3/quota-stats/<bucket>` signé SigV4 (l'utilisateur de l'app n'a besoin que de `s3:GetBucketQuota`). Le quota RustFS ne suffit pas : avant d'ouvrir un upload, vérifier aussi la place restante côté SQL, et traduire « Bucket quota exceeded » en 413.

## Architecture frontend (`frontend/src`)

Structure plate sous `src/` (pas de `features/`), comme NestWiki : `api/` (un wrapper par domaine, enveloppe `ResponseDto`), `components/` (`ui/` = shadcn généré, **ne pas éditer à la main** ; `layout/` = Topbar/Sidebar/AppLayout), `hooks/`, `lib/` (`api-client.ts` : axios `withCredentials`, 401 → refresh puis rejeu, déconnexion si le refresh échoue), `pages/` (une par route, câblées dans `App.tsx`), `schemas/` (zod), `utils/` (fonctions pures). Imports via `#<dossier>/…`. Après login, `sameOriginPath` (`utils/safe-redirect.ts`) n'autorise qu'une redirection vers le site lui-même. Logos et mascotte repris de NestWiki (`public/logo-{light,dark}.svg`, `public/mascot-{light,dark}.png`).

Page `/redirects` (`pages/Redirects.tsx`, `components/links/`, `hooks/useLinks.ts`) : liste, création, modification, désactivation, suppression (dialogue de confirmation) et copie de l'URL `/r/<slug>`, via `api/links.ts`. `schemas/link.schema.ts` reprend les limites de `links/dto/in/link-fields.schema.ts` (longueurs, alphabet, noms réservés : les garder synchronisés) ; en modification, seuls les champs changés partent dans le `PATCH`. Les statuts 400/404/409 sont traduits par `lib/link-errors.ts` (troisième argument de `extractErrorMessage`). Fiche d'un lien `/redirects/:id` (`pages/RedirectDetail.tsx`, chargée en `lazy` pour sortir recharts du bundle principal) : lien, destination, état et stats (`hooks/useLinkDetail.ts`, graphique `components/links/ClicksChart.tsx` sur le composant shadcn `chart`, listes `TopClicksList`) ; la période vient de `?days=` (`utils/link-stats.ts` : options 7/30/90/365, sinon 30).

Pages `/shares` et `/shares/:id` (`pages/Shares.tsx`, `pages/ShareDetail.tsx`, `components/shares/`, `hooks/useShares.ts`, `hooks/useShareDetail.ts`, `api/shares.ts`) : même découpage que les redirections, `schemas/share.schema.ts` reprend les limites du backend (`SHARE_MAX_DOWNLOADS_LIMIT`, `FILE_MAX_SIZE_BYTES`, longueur du nom : les garder synchronisés, slug et expiration réutilisent `link.schema.ts`), erreurs traduites par `lib/share-errors.ts` (`shareErrorMessages` pour le partage, `uploadErrorMessage` pour l'envoi). `useShareDetail` relit la fiche toutes les `FILE_STATUS_POLL_MS` tant qu'un fichier est en `verifying`, et à chaque fin d'envoi.

Page `/files` (`pages/Files.tsx`, `components/files/`, `hooks/useFiles.ts`, `api/files.ts`) : fichiers stockés, état, origine (lien vers `/shares/:id` tant que le partage existe) et barre de place (`FilesUsage`). Le filtre « Orphelins » vit dans l'URL (`?orphans=true`, toute autre valeur = tous ; `listFiles` n'envoie jamais `orphans=false`, le backend répondrait 400). Erreurs traduites par `lib/file-errors.ts`, une table par route car le 409 change de sens (suppression : encore attaché à un partage ; téléchargement : pas prêt). `useFiles` renvoie `reload` (repasse par le chargement) et `refresh` (relit sans squelette, après une suppression) ; une réponse périmée est ignorée. Après une suppression réussie, ou refusée en 404/409 (le fichier a changé ailleurs), la liste est relue et la jauge du Sidebar aussi (`refreshStorageUsage` de `lib/storage-usage-refresh.ts`, écouté par `useStorageUsage`). Le bouton supprimer d'un fichier `inUse` est désactivé, avec l'infobulle `title` sur son `span`.

**Envoi de fichiers** : `UploadsProvider` (monté dans `AppLayout`, l'envoi survit à un changement de page ; `beforeunload` tant qu'un envoi tourne, tout est arrêté sans rien supprimer à la déconnexion) porte une `UploadQueue` (`lib/upload-queue.ts`, lue par `useUploads(shareId)` via `useSyncExternalStore`) : un fichier à la fois, `revision` monte à chaque fin d'envoi. `lib/share-upload.ts` déroule `uploadNewFile` et `resumeFile` : empreinte (`lib/file-hash.ts` → `lib/sha256.worker.ts` → `utils/file-sha256.ts` : `@noble/hashes`, pur JS car la CSP refuse le wasm, tranches `File.slice` de `SHA256_CHUNK_BYTES`, jamais le fichier entier ; le worker est un chunk same-origin de `/assets/`, donc `script-src 'self'` suffit, ne pas passer en worker `blob:`), annonce, parts par `file.slice` (`utils/file-parts.ts`, `PART_CONCURRENCY` en parallèle), relance d'une part seule sur erreur réseau, 408, 429 (`Retry-After`) ou 5xx, `PART_MAX_ATTEMPTS` essais au plus, puis `complete`. Annuler = `DELETE` du fichier s'il est déjà ouvert côté serveur, y compris pour une reprise. Le slug d'un partage est verrouillé pendant un envoi (les parts le visent). **Reprise** : `utils/pending-uploads.ts` garde dans `localStorage` les métadonnées de chaque envoi ouvert, jamais le contenu (clé `fileId`, entrées oubliées quand le fichier n'est plus `uploading` et n'a plus de ligne dans la file, échec compris : la fiche ne connaît pas encore un fichier ouvert depuis son dernier chargement) ; avec une entrée, le fichier re-sélectionné doit avoir mêmes nom, taille et `lastModified`, et le hash mémorisé évite de le recalculer ; sans entrée, même taille puis SHA-256 recalculé égal à celui renvoyé par `GET …/parts`, sinon `DifferentFileError`, sans rien envoyer ; seules les parts absentes ou de mauvaise taille repartent (`missingParts`).

shadcn CLI : il résout mal les alias `#…` (fichiers écrits hors de `src/`, dépendance parasite `cn`). Générer les composants dans un projet jetable aux alias `@/` avec le même `components.json`, puis les copier dans `components/ui/` en remplaçant seulement les imports par `#lib/utils` et `#components/ui/…`.

## Langue (i18n)

Comme NestWiki : l'interface est en français ou en anglais, au choix de l'admin, pour tout le site (pages publiques `/d/` et `/u/` comprises). Le réglage `locale` vit en base (`system_settings`, module `settings/`) : `GET /api/settings` est public (lu par `main.tsx` avant le premier rendu, pour que la page de login soit déjà dans la bonne langue), `PATCH /api/settings/locale` exige la session et passe dans le journal d'audit. Front : `react-i18next`, `lib/i18n.ts` (`applyLocale`), un seul fichier par langue (`locales/fr.json`, `locales/en.json`, mêmes clés : `locales.test.ts` le vérifie). **Aucun texte affiché en dur** : toute chaîne nouvelle passe par `t()` et entre dans les deux fichiers ; les schémas zod du front prennent `t` (`createLoginSchema(t)`). Les messages d'erreur de l'API restent en anglais ; le front traduit ceux qu'il sait reconnaître (statut 401 au login, 429…). Page `/settings` : langue et mot de passe.

## Règles transverses du plan

- Redirections en **302** uniquement (destination modifiable), jamais 301.
- Même 404 pour un lien inexistant, désactivé ou supprimé ; 410 + page « lien expiré » pour un lien expiré.
- Destinations en `http`/`https` uniquement, longueur max ; slugs limités à un alphabet, hors noms réservés.
- Uploads multipart du navigateur vers le backend, qui les transmet en flux à S3, parts < 100 Mo (limite du Cloudflare Tunnel) ; taille et SHA-256 vérifiés en fin d'upload, MIME détecté côté serveur, refus pendant l'envoi (413).
- Opérations multi-étapes en transaction ; contraintes en base (FK, unicité des IDs publics, `NOT NULL`).
- Tout est modifiable après création (destination, limites, expiration).

## Git

Branches `main` (déploiement) et `dev` (intégration) ; une branche par ticket, PR vers `dev`. CI (`.github/workflows/ci.yml`) : lint, tests, build, `pnpm audit`, images Docker (poussées sur GHCR depuis `main`), actions épinglées par commit ; Dependabot mensuel sur `dev` (mineures et correctifs npm groupés en une PR, majeures de `typescript` ignorées tant que typescript-eslint ne supporte pas TS 7). `pnpm-workspace.yaml` porte les `overrides` (`minimatch` >= 11.0.1) et `auditConfig.ignoreGhsas` (chaque entrée justifiée en commentaire) : `pnpm audit` complet doit rester propre.

**Version** : `0.<plan>.<ticket>`, identique dans les trois `package.json` (racine, `backend`, `frontend`), un bump par ticket. Chaque plan de `/dev-plan` prend le numéro suivant et pose le label `plan:0.<n>` sur ses tickets : son premier ticket fusionné ouvre `0.<n>.0`, les suivants montent le dernier chiffre. Un ticket sans label `plan:` monte seulement le dernier chiffre. Deux tickets en parallèle : le second à fusionner reprend le numéro suivant au rebase.

**Changelog** : chaque ticket ouvre sa section `## <version> — <AAAA-MM-JJ>` en tête de `CHANGELOG.md`, sans section « Non publié ». En français, du point de vue de l'utilisateur, sur le modèle de `../wiki/CHANGELOG.md` : une puce par changement, pas de détail d'implémentation ni de mention des tickets à venir, préfixes `Sécurité :` et `Dépendances :` si utile, ⚠️ avec l'action exacte si la mise à jour en demande une.
