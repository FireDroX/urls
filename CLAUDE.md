## Projet

**url.addrien.fr** — outil perso qui regroupe trois usages derrière un seul compte admin : raccourcir des URL (`/r/<id>`), partager des fichiers (`/d/<id>`) et en recevoir (`/u/<id>`). Même architecture que NestWiki (`../wiki`, à consulter pour tout pattern déjà résolu là-bas) : pnpm workspace avec `backend/` (NestJS + TypeORM + MySQL 8) et `frontend/` (React + TypeScript + Vite, TailwindCSS + shadcn/ui).

Le plan de référence est `Plan url.addrien.fr.md` (phases 0 à 4, exigences de sécurité transverses) et la maquette `Maquette url.addrien.fr.html` (thème sombre, Montserrat / Noto Sans, accent orange) ; les deux restent hors dépôt (`.gitignore`). Une fonctionnalité n'est terminée qu'avec ses limites, ses codes d'erreur et ses contrôles d'intégrité.

État : phases 1 (redirections `/r/`) et 2 (partages `/d/`, fichiers stockés) livrées. **Phase 3** (dépôts `/u/`) : colonnes et API admin des dépôts (`/api/drops`), aperçu public, API publique d'envoi de fichiers, page publique `/u/:id`, fiche admin `/drops/:id` (fichiers reçus) et création d'un partage à partir d'un dépôt en place. **Phase 4** : table et API admin des tags (`/api/tags`), table et API admin des dossiers (`/api/folders`), page admin `/organization` (tags et dossiers), choix et affichage des tags et du dossier dans les formulaires, tables et fiches des liens.

## Commandes

Toujours lancer l'app via les scripts `pnpm run <script>` du package concerné. Ports de dev : backend `:3001`, frontend `:5174` (NestWiki occupe déjà `:3000`/`:5173`) ; vérifier les ports avant de lancer un serveur, et arrêter ceux qu'on a lancés (`netstat -ano | grep ":3001"`, puis `taskkill //F //PID <pid>`).

```bash
cd backend && pnpm run start:dev    # API en watch (http://localhost:3001/api)
cd frontend && pnpm run dev         # Vite, proxifie /api et /r/ vers VITE_API_PROXY_TARGET
```

Backend (`backend/`) :

```bash
pnpm run lint                # eslint --fix
pnpm run test                # vitest
pnpm run build
pnpm run migration:run       # applique les migrations TypeORM en attente
pnpm run migration:revert    # annule la dernière migration
pnpm run migration:generate  # diff entities vs DB — à relire, jamais pris tel quel
pnpm run seed:admin          # crée le compte admin depuis ADMIN_* si la base n'a aucun compte (idempotent, lancé par entrypoint.sh ; Nest refait la même vérification au démarrage)
```

Frontend (`frontend/`) : `pnpm run lint` (oxlint), `pnpm run test` (vitest + jsdom), `pnpm run build`.

## Environnement

Dev : la base et le S3 tournent sur la VM docker de dev `192.168.2.64` (stack `/opt/nestwiki-dev` : MySQL 8.4 sur `:3306`, RustFS sur `:9000`), partagés avec NestWiki : base `urls`, utilisateur MySQL `urls` limité à `urls.*`, bucket `urls` et utilisateur S3 `urls` limité à ce bucket. `infra/rustfs/setup.sh` (local, **hors dépôt** : `infra/` est dans `.gitignore`) crée bucket, utilisateur, politique, quota et CORS (le CORS du bucket ne sert plus à l'upload, qui passe par le backend ; idempotent, avec le compte admin RustFS — jamais celui de l'app).

Config : trois `.env`, chacun avec un `.env.example` à copier.

- racine — lu par `docker compose` uniquement (mots de passe MySQL/RustFS du compose complet, réseaux externes de prod, `VITE_TURNSTILE_SITE_KEY` pour le build de l'image frontend).
- `backend/.env` — `PUBLIC_URL` (origine publique : CORS, cookies `Secure` si `https://`), `DB_*`, `JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET`, `IP_HASH_SECRET` (clé HMAC des IP des visiteurs, 32 caractères min.), `ADMIN_EMAIL`/`ADMIN_PASSWORD`, `S3_ENDPOINT` (accès interne), `S3_PUBLIC_ENDPOINT` (hôte public qui **signe** les URLs présignées — `https://cdn.addrien.fr` en prod, la signature couvre l'hôte), `S3_ACCESS_KEY`/`S3_SECRET_KEY`/`S3_BUCKET`/`S3_REGION`, `TURNSTILE_SECRET_KEY`, `CLIENT_IP_HEADER` (`cf-connecting-ip` derrière le tunnel) et `TRUST_PROXY_HOPS`. **`validateEnvironment` (`src/config/env.validation.ts`) bloque le démarrage** si un secret est absent, trop court ou une valeur par défaut connue (`KNOWN_DEFAULT_SECRETS`), si les deux secrets JWT sont identiques, ou si `TURNSTILE_SECRET_KEY` manque alors que `PUBLIC_URL` est en `https://` — sauf `DEV=true` (dev local uniquement, jamais en prod).
- `frontend/.env` — `VITE_API_URL` (`/api` : même origine, nginx en prod et le proxy Vite en dev), `VITE_API_PROXY_TARGET`, `VITE_TURNSTILE_SITE_KEY`.

Ne jamais afficher ni copier les valeurs des `.env` : générer de nouveaux secrets (`openssl rand -hex 32`).

## Déploiement

- `docker-compose.yml` : stack complète (mariadb + rustfs + backend + frontend, plus `storage-init` en profil `setup`, qui monte `infra/rustfs`), pour un serveur vierge ou un essai local. Réseaux `database` et `storage` en `internal`, partagés seulement avec le backend ; seul le frontend publie un port (`127.0.0.1:8081`), servi par le Cloudflare Tunnel.
- `docker-compose.external.yml` : prod, la base et le RustFS existent déjà (ceux de NestWiki, S3 exposé sur `cdn.addrien.fr`). La base de prod est un `mariadb:11` (comme `docker-compose.yml`), celle de la VM de dev un MySQL 8.4 : les migrations doivent passer sur les deux (`DROP CONSTRAINT`, jamais `DROP CHECK`, contrôlé par `migrations-portability.spec.ts`). Images `ghcr.io/firedrox/urls-{backend,frontend}` poussées par la CI sur `main`, réseaux externes `DATABASE_NETWORK`/`STORAGE_NETWORK` (réseaux `--internal` dédiés).
- Backend : utilisateur `node` (non root), `mem_limit`, `read_only`, `no-new-privileges`. `entrypoint.sh` lance migrations, seed admin puis l'API. Le frontend nginx proxifie `/api/` et `/r/` vers `backend:3000` (la route des parts d'upload a sa propre `location` : `client_max_body_size 33m`, `proxy_request_buffering off`, le reste de `/api/` garde la limite de 1 Mo) et envoie la CSP (scripts du site + Turnstile seulement), `nosniff`, `X-Frame-Options`.

## Architecture backend (`backend/src`)

NestJS, un module par domaine directement sous `src/` (pas de dossier `modules/`) : `audit`, `auth`, `drops`, `events`, `files`, `folders`, `health`, `links`, `security`, `settings`, `shares`, `storage`, `tags`, `users`, plus `common/` (filtres, DTOs, exceptions, guards, décorateurs, stratégie JWT, constantes), `config/` (TypeORM, validation de l'environnement) et `database/` (migrations, seed admin). Pour créer un module : skill `new-backend-module`.

Même découpage en couches que NestWiki :

- `<module>.controller.ts` — HTTP uniquement : un appel au service, puis le mapper construit la réponse. Routes protégées par `@UseGuards(JwtAuthGuard)` (un seul compte : pas de rôles) ; toujours `@UseFilters(<Module>ExceptionFilter)`.
- `services/*.service.ts` — logique métier **et validation**. Pas de `class-validator` ni de `ValidationPipe` : le controller reçoit `@Body() body: unknown`, le service le passe à `parseDto(<schema>, body)` (`common/parse-dto.ts`), qui lève `ValidationException` (400). Lève des exceptions de domaine depuis `common/exceptions/<domaine>/*.exception.ts` (`extends Error`, `this.name = '<NomDeClasse>'`).
- `dto/in/*.dto.ts` — un schéma `zod` (`z.strictObject`, longueurs max, normalisation) et le type inféré. `dto/out/*.dto.ts` — une `interface`, enveloppée dans `ResponseDto<T>`.
- `entities/*.entity.ts` — entités TypeORM ; le schéma appartient aux migrations SQL brutes (`src/database/migrations/`, `queryRunner.query`), **jamais** `synchronize: true`. Noms explicites pour index et clés étrangères.
- `persistence/` — port (interface) + adapter `typeorm.*.repository.ts`, injecté via un **token string littéral** au pluriel (`'UsersRepository'`, `'AuditLogsRepository'`) : il doit différer de `` `${EntityName}Repository` ``, déjà enregistré par `@nestjs/typeorm`.
- `mapper/*.mapper.ts` — classe statique entity → DTO qui construit le `ResponseDto`.
- `filter/*.exception.filter.ts` — `@Catch()` par module, table `exception.name` → statut ; un nom inconnu part dans `HttpExceptionFilter.respond`.

**Erreurs** : format unique `{ error: '<message>' }` (messages en anglais). `common/filters/http-exception.filter.ts` (aussi filtre global) garde le vrai statut des `HttpException` et des erreurs body-parser exposées (400, 413…), et répond `500 Internal server error` sans jamais exposer le message interne (SQL, stack), qu'il logge. Jamais de 500 pour une erreur client : chaque exception de domaine doit être mappée dans le filtre de son module (et ceux des modules qui l'appellent).

**`common/variables.global.ts`** centralise les constantes (longueurs, durées, limites de débit, alphabet des IDs publics…) : y ajouter les nouvelles.

**IDs publics** : `generatePublicId()` (`common/public-id.ts`, nanoid base62, 8 caractères). Ne jamais exposer un ID SQL (uuid interne) dans une réponse ou une URL.

**Auth** : un seul compte, créé depuis `ADMIN_*` (`database/default-admin.ts`). Mot de passe hashé en argon2id (`common/password.ts`, `@node-rs/argon2`). JWT access 15 min + refresh 7 j en cookies `httpOnly`, `SameSite=Strict`, `Secure` si `PUBLIC_URL` est en `https://`. `JwtStrategy` → `SessionUserResolver` recharge l'utilisateur à chaque requête et refuse un jeton antérieur au dernier changement de mot de passe (qui déconnecte donc les autres sessions). Verrouillage après `MAX_FAILED_LOGIN_ATTEMPTS` échecs (423 + `Retry-After`), compteur remis à zéro à l'expiration. Turnstile vérifié côté serveur (`security/services/turnstile.service.ts`) avec l'IP cliente réelle.

**IP cliente et rate limits** : `resolveClientIp` (`common/client-ip.ts`) lit `CLIENT_IP_HEADER` (`cf-connecting-ip` en prod) sinon `req.ip`, calculé par Express avec `trust proxy = TRUST_PROXY_HOPS`. `ThrottlerBehindProxyGuard` (global, 100 req/min) l'utilise ; `@Throttle` plus strict sur l'auth. Le throttler répond 429 avec `Retry-After`, affiché par le front (`lib/api-errors.ts`).

**Audit** : `AuditLogService.record` (`audit/`) journalise connexions (réussies, échouées, verrouillées), changements de mot de passe et de réglages, et créations, modifications et suppressions de liens, de tags et de dossiers (`AuditAction`).

**Liens** (`links/`) : une seule table `links` pour les trois types (`redirect`, puis `share` et `drop`), contrainte `CHECK` sur le type et sur la destination obligatoire d'une redirection. `public_id` = slug choisi ou `generatePublicId()`, unique et en `utf8mb4_bin` (sensible à la casse, comme l'alphabet base62). API admin `GET/POST /api/links`, `GET/PATCH/DELETE /api/links/:id` (`:id` = `public_id`) ; tout est modifiable (destination, slug, expiration, désactivation). Suppression en soft delete (`deleted_at`) : le slug d'un lien supprimé reste pris (409), pour qu'une ancienne URL partagée ne pointe jamais vers une autre destination. Limites (longueurs, alphabet du slug, noms réservés, throttle de création) dans `variables.global.ts`.

**Redirection publique `/r/:id`** (`links/redirects.controller.ts`) : seule route hors du préfixe `/api` (`exclude` de `setGlobalPrefix` dans `main.ts`), servie par le backend pour répondre côté serveur. Lien actif → `302` vers la destination, `Cache-Control: no-store` (jamais de 301 ni de cache). Lien inexistant, désactivé, supprimé ou id mal formé (vérifié avant toute requête SQL) → même `LinkNotFoundException` (404, corps et en-têtes identiques) ; `expires_at` passé → `LinkExpiredException` (410). `@Throttle` dédié (`LINK_REDIRECT_THROTTLE_*`, par IP via `resolveClientIp`). Les pages 404/410 sont celles de la SPA, statut conservé : nginx (`proxy_intercept_errors` + `error_page 404 410 /index.html`) et le proxy Vite (plugin `public-link-proxy` de `vite.config.ts`) remplacent le corps JSON par `index.html` ; la route `/r/:id` du front (`RedirectUnavailable`) relit le statut par un `fetch` sans suivre la redirection (`redirect: 'manual'`) et affiche « lien introuvable » ou « lien expiré » dans la langue du site. Les 429 passent tels quels (`Retry-After` conservé).

**Événements** (`events/`, port `'EventsRepository'`, entité `LinkEvent`) : table `events` (`link_id` → `links.id` en `ON DELETE CASCADE`, `type` contraint par `CHECK`, index `(link_id, created_at)` pour les stats). Un `302` de `/r/:id` appelle `EventsService.recordClick` sans l'attendre (les 404/410/429 n'enregistrent rien) ; le décorateur `@CurrentVisitor()` (`common/visitor.ts`) fournit l'IP (`resolveClientIp`), `Referer`, `User-Agent` et `CF-IPCountry`. Referer et user-agent tronqués (`EVENT_*_MAX_LENGTH`), pays gardé seulement s'il fait 2 lettres (`XX`, `T1` → `null`), IP stockée uniquement en HMAC-SHA-256 hex avec `IP_HASH_SECRET` : jamais en clair, ni en base ni dans les logs. Un échec d'insertion est loggé, la redirection part quand même. Stats : `GET /api/links/:id/stats?days=N` (`LinksService.stats` valide `days` par `linkStatsQuerySchema` : entier de `LINK_STATS_MIN_DAYS` à `LINK_STATS_MAX_DAYS`, `LINK_STATS_DEFAULT_DAYS` par défaut, tout autre paramètre → 400 ; lien inconnu ou supprimé → 404), agrégée en SQL par l'adapter (`GROUP BY` sur l'index `(link_id, created_at)` : clics par jour, top `LINK_STATS_TOP_LIMIT` sources et pays, `null` = direct / pays inconnu). Les sources sont groupées par hôte : `referer_host`, rempli à l'insertion par `refererHost` (`common/referer-host.ts` : hôte en minuscules sans port, `null` si le referer est absent, invalide ou non http(s)), l'API renvoie `referers: [{ host, clicks }]` ; `EventsService.clickStats` complète les jours sans clic à 0. **Jours en UTC** (`created_at` est écrit en UTC : `timezone: 'Z'` côté pilote, et `config/mysql-connection.ts` envoie `SET time_zone = '+00:00'` sur chaque connexion du pool — app, migrations et seed partagent `mysqlConnectionOptions` —, pour les `CURRENT_TIMESTAMP` remplis par MySQL) : la fenêtre commence à minuit UTC il y a `N - 1` jours, aujourd'hui inclus, et la réponse porte `timeZone: 'UTC'`.

**Vérification des destinations** (`links/`, port `'LinkChecksRepository'`, entité `LinkCheck`) : table `link_checks` (une ligne par lien, `link_id` PK et FK `FK_link_checks_link` en `ON DELETE CASCADE`, `outcome` ∈ `ok` | `broken` | `skipped`, `status_code` et `error_kind` nullables, `error_kind` ∈ `dns`, `connection`, `tls`, `timeout`, `too_many_redirects`, `invalid_redirect`, tous contraints par `CHECK`, `consecutive_failures`, `checked_at`). `POST /api/links/:id/check` (`LinkChecksService`, `JwtAuthGuard`, `@Throttle` `LINK_CHECK_THROTTLE_*`, redirection inconnue, supprimée ou mal formée → 404, une redirection désactivée ou expirée reste vérifiable) renvoie `{ id, outcome, statusCode, errorKind, consecutiveFailures, checkedAt }`. `DestinationProbe` suit les sauts à la main (`LINK_CHECK_MAX_REDIRECTS`, budget total `LINK_CHECK_TIMEOUT_MS` pour le DNS, chaque saut et les replis) : `http`/`https` seulement, DNS résolu puis refus (`skipped`, rien n'est envoyé) si **une** adresse échoue `isPublicAddress` (`common/network-address.ts` : v4 loopback, privé, link-local dont `169.254.169.254`, CGNAT, multicast, réservé ; v6 en liste blanche `2000::/3` hors Teredo, documentation, 6to4 ; IPv4 mappée jugée sur son IPv4 ; échec fermé), chaque saut de redirection revérifié. `PinnedHttpTransport` (seul fichier qui fait du réseau, aucune politique) se connecte à l'IP vérifiée (`lookup` figé : pas de second DNS, SNI et `Host` gardés), HEAD puis GET sur 405/501, corps jamais lu, ni cookie ni identifiant, `LINK_CHECK_USER_AGENT` générique. 2xx/3xx → `ok`, 4xx/5xx ou erreur réseau → `broken`. L'adapter écrit en une requête `INSERT … ON DUPLICATE KEY UPDATE` : `broken` ajoute 1 à `consecutive_failures`, `ok` le remet à 0, `skipped` le laisse. Aucun log ni audit ne contient la destination, un hôte, un `Location` ou la réponse distante. **Passe quotidienne** : `LinkCheckSweepService` (`@Cron(LINK_CHECK_CRON)` en UTC, `0 4 * * *`, via `ScheduleModule.forRoot()` d'`app.module.ts`, `@nestjs/schedule`) ne fait aucune requête sortante hors de `LinkChecksService.checkLink` → `DestinationProbe`. Verrou en mémoire : une passe qui démarre pendant la précédente est ignorée (warn, `null`) sans rien lire ; le verrou est relâché en `finally`, y compris si la lecture échoue (loggée sans message, `run` ne rejette jamais). `findRedirectsDueForCheck` (redirections non supprimées, désactivées ou expirées comprises, jamais vérifiées d'abord puis `checked_at` croissant, `created_at` en départage) en prend `LINK_CHECK_BATCH_SIZE`, relues une à une par `LinksService.get` juste avant leur vérification (une redirection supprimée ou dont le slug a changé depuis la lecture du lot est comptée `gone`, sans requête sortante ; une destination modifiée est vérifiée dans sa nouvelle valeur) puis vérifiées avec `LINK_CHECK_DELAY_MS` entre deux (pas après la dernière) ; une erreur sur un lien est comptée et loggée avec son `publicId` et le nom de l'erreur seulement, la passe continue. Un seul log de bilan par passe (vérifiées, ok, cassées, ignorées, disparues, erreurs), sans destination. Au plus `LINK_CHECK_BATCH_SIZE` redirections par passe : au-delà, chacune est revérifiée tous les quelques jours. Un `PATCH` qui change la destination supprime la ligne `link_checks` du lien dans la même transaction que la sauvegarde (`saveWithCheckReset`) ; un contrôle en cours pendant le `PATCH` peut écrire un résultat pour l'ancienne destination, corrigé à la passe suivante.

**Partages** (`shares/`, port `'SharesRepository'` sur l'entité `Link` limitée au type `share`) : API admin `GET/POST /api/shares`, `GET/PATCH/DELETE /api/shares/:id` (`:id` = `public_id`), mêmes règles de slug que les redirections (`slugSchema`, `expiresAtSchema` de `links/dto/in/link-fields.schema.ts`, id mal formé → 404 avant SQL via `isWellFormedLinkId` de `common/public-id.ts`, 409 si pris), `maxDownloads` facultatif (1 à `SHARE_MAX_DOWNLOADS_LIMIT`, `CHECK` en base : seulement pour un `share`), `downloadCount` en lecture seule, `SHARE_FILES_MAX` fichiers au plus par partage (appliqué à l'upload) ; tout est modifiable, soft delete, audit `shares.*`. La liste donne `fileCount`/`totalSize` par partage (agrégés en SQL), la fiche ajoute `files` (`publicId`, nom, taille, MIME, statut). **Fichiers** (`files/`, entité `StoredFile`, port `'FilesRepository'`, `FilesService` exporté) : table `files` (`link_id` → `links.id` en `ON DELETE RESTRICT` : un lien ne se supprime jamais en dur tant que des lignes de fichiers le référencent ; `s3_key` unique, `size` en `bigint` converti en nombre, `sha256` annoncé contrôlé par `CHECK`, `status` ∈ `FILE_STATUSES` (`uploading` → `verifying` → `ready` | `rejected`), `upload_id` multipart, soft delete). `isDuplicateEntry` (`common/database-errors.ts`) traduit `ER_DUP_ENTRY`.

**Upload multipart via le backend** (`shares/share-files.controller.ts` → `ShareFilesService` → `files/services/file-uploads.service.ts`, admin, `JwtAuthGuard`, filtre `ShareFilesExceptionFilter`) : le navigateur n'écrit jamais dans S3, il envoie ses parts au backend qui les transmet en flux à `UploadPart` par le client interne : pas d'URL d'upload présignée, pas de CORS sur le bucket, pas de CSP à élargir.

- `POST /api/shares/:id/files` (`{ name, size, sha256 }`, `files/dto/in/start-upload.dto.ts` : nom réduit à son nom de base, sans caractères de contrôle ni invisibles, 1 à `FILE_NAME_MAX_LENGTH` ; SHA-256 hex normalisé en minuscules) : `size` > `FILE_MAX_SIZE_BYTES` → 413 ; puis `CreateMultipartUpload` sous une clé opaque `files/<uuid>` et `insertWithinLimits` (adapter : transaction, `SELECT … FOR UPDATE` sur le lien, plus de `SHARE_FILES_MAX` fichiers → 413, somme SQL des tailles non rejetées ni supprimées + taille annoncée > `FILES_STORAGE_QUOTA_BYTES` → 413) ; un refus annule l'upload multipart. Réponse : `fileId`, `partSize` (`FILE_PART_SIZE_BYTES`, 32 Mio), `partCount`, `file`.
- `PUT …/files/:fileId/parts/:n` : `n` de 1 à `partCount` et `Content-Length` égal à la taille attendue de la part, `Transfer-Encoding` refusé (400) ; le corps (jamais en mémoire) passe par `measuredPart` (`files/file-streams.ts` : coupe en 413 au-delà, 400 si plus court ou client parti) puis `UploadPart`. Le parseur JSON ignore cette route (`common/json-body.ts`, option `type` de `useBodyParser` dans `main.ts`). `@Throttle` dédié (`FILE_PART_THROTTLE_LIMIT`). Une part se renvoie seule.
- `GET …/files/:fileId/parts` : reprise d'un upload. `ListParts` d'un fichier `uploading` : `fileId`, `size`, `sha256` annoncé, `partSize`, `partCount`, `parts: [{ partNumber, size }]` (ni clé S3, ni `upload_id`, ni ETag) ; fichier inconnu, d'un autre partage ou supprimé → 404, plus en `uploading` → 409.
- `POST …/files/:fileId/complete` : `ListParts` (nombre et taille de chaque part, sinon 409), `CompleteMultipartUpload` (« Bucket quota exceeded » → `StorageQuotaExceededException`, 413), passage conditionnel `uploading` → `verifying` (sinon 409 ; si la ligne a été supprimée entre-temps, l'objet est effacé et un nettoyage raté est loggé avec sa clé sans changer la réponse, l'objet d'un `complete` concurrent sur une ligne vivante n'est jamais touché), 202. `FileVerificationService` vérifie en tâche de fond (`HeadObject` pour la taille, SHA-256 recalculé en relisant l'objet en flux, MIME détecté par `file-type` sur les `FILE_MIME_SNIFF_BYTES` premiers octets, `application/octet-stream` à défaut) → `ready`, sinon `rejected` et objet supprimé ; une erreur de stockage laisse le fichier en `verifying`, repris au démarrage suivant (`onApplicationBootstrap`).
- `DELETE …/files/:fileId` : passe par `FileDeletionService.erase` (voir « Fichiers stockés »), 503 si le stockage est injoignable. Audit `files.created` / `files.deleted`.
- Fichier inconnu ou d'un autre partage → 404, plus en `uploading` (ou upload inconnu de S3, `NoSuchUpload`) → 409, stockage injoignable → 503. Le client S3 est réglé en `requestChecksumCalculation`/`responseChecksumValidation` `WHEN_REQUIRED` (`S3_CHECKSUM_MODE`) : pas d'encodage `aws-chunked` sur les parts envoyées en flux.

**Fichiers stockés** (`files/files.controller.ts` → `FilesAdminService`, admin, filtre `FilesExceptionFilter`) : `GET /api/files` liste les fichiers non supprimés, du plus récent au plus ancien, chacun avec `inUse` et son lien (`type`, `publicId`, `deleted`, `disabled`, `expired` via `isLinkUsedUp` de `common/link-expiry.ts`) ; `?orphans=true` (seule valeur admise, tout autre paramètre → 400) ne garde que les orphelins. Règle `isFileInUse` (`files/file-usage.ts`) : un fichier est utilisé si son lien est un `share` ou un `drop` non supprimé, même désactivé, expiré ou plein ; un fichier d'un partage ou d'un dépôt supprimé est orphelin. `summary` (toujours sur tous les fichiers) : `quotaUsedBytes` (même règle SQL que `insertWithinLimits`, `COUNTED_FILES`), `quotaLimitBytes` (`FILES_STORAGE_QUOTA_BYTES`), `orphanBytes` (orphelins hors `rejected`) et `storageUsedBytes` (usage réel de RustFS, `null` s'il est injoignable). `DELETE /api/files/:id` : id inconnu, mal formé ou supprimé → 404, fichier utilisé → 409, sinon `FileDeletionService.erase(file, link, { action, userId })` (l'action d'audit est choisie par l'appelant : `files.deleted`, ou `drops.files.cancelled` sans `userId` pour un visiteur ; chemin unique, aussi utilisé par `DELETE /api/shares/:id/files/:fileId`) : `AbortMultipartUpload` si `uploading` (`NoSuchUpload` → `DeleteObject`), sinon `DeleteObject` (objet déjà absent = succès), **puis** soft delete de la ligne ; pour tout fichier lu en `uploading` (Abort réussi ou `NoSuchUpload`), un `DeleteObject` part **après** le soft delete et **avant** l'audit `files.deleted`, et sur le chemin `NoSuchUpload` un premier `DeleteObject` part aussi avant le soft delete (son échec donne 503, la ligne reste, un nouveau `DELETE` reprend ; un `complete` concurrent a pu aboutir malgré l'abandon : si son passage à `verifying` a précédé le soft delete, c'est ce `DeleteObject` qui efface l'objet, sinon `complete` le nettoie lui-même), au mieux : un échec est loggé avec la clé de l'objet et `erase` se termine quand même par son audit ; stockage injoignable → 503, la ligne reste et un nouveau `DELETE` reprend. `POST /api/files/:id/download` : fichier `ready` → `{ url }` présignée `FILE_DOWNLOAD_URL_TTL_SECONDS` en `attachment`, autre statut → 409, sans toucher à `download_count` ni aux événements.

**Page publique `/d/:id`** : route SPA (`pages/ShareDownload.tsx`, hors layout admin, servie par le `location /` de nginx) qui lit `GET /api/public/shares/:id` (`shares/public-shares.controller.ts` → `PublicSharesService`, sans session, `@Throttle` `SHARE_VIEW_THROTTLE_*`, `Cache-Control: no-store`) : fichiers `ready` seulement (`publicId`, nom, taille), nombre, taille totale, `expiresAt`. Id mal formé, inexistant, désactivé, supprimé ou sans fichier prêt → même `ShareNotFoundException` (404) ; expiré ou `download_count >= max_downloads` → `ShareExpiredException` (410). Un 200 appelle `EventsService.recordView` sans l'attendre. `POST /api/public/shares/:id/files/:fileId/download` (`{ turnstileToken }`, `@Throttle` `SHARE_DOWNLOAD_THROTTLE_*`) : Turnstile vérifié avec l'IP réelle avant toute lecture (400 sinon), puis `incrementDownloadCount` (un seul `UPDATE` gardé par `download_count < max_downloads`, expiration, désactivation et soft delete : la course sur le dernier téléchargement donne un seul gagnant, l'autre reçoit 410), `recordDownload`, et URL présignée `SHARE_DOWNLOAD_URL_TTL_SECONDS` signée par `S3_PUBLIC_ENDPOINT` en `attachment` avec le nom d'origine ; le front y navigue (`utils/start-download.ts`) et redemande un jeton Turnstile après chaque essai. `events.type` ∈ `EVENT_TYPES` (`click`, `view`, `download`, `upload`) ; la fiche admin d'un partage ajoute `viewCount` (`EventsService.countViews`) à `downloadCount`.

**Dépôts** (`drops/`, port `'DropsRepository'` sur l'entité `Link` limitée au type `drop`) : API admin `GET/POST /api/drops`, `GET/PATCH/DELETE /api/drops/:id` (`:id` = `public_id`), mêmes règles de slug, d'expiration, de 404 avant SQL, de 409, de soft delete que les partages ; audit `drops.*`. Colonnes de `links` : `title` (facultatif, `DROP_TITLE_MAX_LENGTH`, sans caractère de contrôle), `max_total_bytes` (`bigint`, 1 à `FILES_STORAGE_QUOTA_BYTES`) et `max_files` (1 à `SHARE_FILES_MAX`, un dépôt tient donc toujours dans un partage) ; `CHECK` nommés `CHK_links_drop_max_total_bytes` / `CHK_links_drop_max_files` : obligatoires et > 0 pour un `drop`, `NULL` sinon. Le transformer `bigintToNumber` (`common/bigint-to-number.ts`) garde `null` à `null` : la colonne est `NULL` pour tous les autres types. Les deux limites sont obligatoires à la création, modifiables ensuite et peuvent descendre sous l'usage courant (le dépôt devient `full`, rien n'est supprimé). La fiche (`GET /api/drops/:id`) ajoute `viewCount` (`EventsService.countViews`) et `files` (`publicId`, nom, taille, MIME, statut, `uploaderName`, dates : jamais d'uuid, de clé S3, d'`upload_id` ni de hash) ; `DELETE /api/drops/:id/files/:fileId` (admin, `DropsService.removeFile`) passe par `FileDeletionService.erase` avec l'audit `files.deleted` **sans** jeton d'envoi (l'admin n'utilise pas `FileUploadsService.find`) : dépôt ou fichier inconnu, mal formé ou d'un autre dépôt → 404, stockage injoignable → 503 et la ligne reste, un envoi `uploading` est annulé, un dépôt désactivé, expiré ou plein reste gérable. La liste et la fiche donnent `fileCount`/`totalSize` (agrégés en SQL par `summarizeCountedByLinkIds`, règle `COUNTED_FILES` : ni rejetés ni supprimés, contrairement à `summarizeByLinkIds` des partages) et `state` ∈ `DROP_STATES`, calculé par `dropState` (`common/drop-state.ts`, appelée par `DropsService`) selon la précédence `disabled` > `expired` > `full` > `open` ; `full` dès que le nombre ou les octets atteignent la limite, ou si une limite est `null` (échec fermé). L'expiration passe par `isLinkExpired` (`common/link-expiry.ts`). `POST /api/drops/:id/share` (admin, `@Throttle` de création, `{ fileIds, slug?, expiresAt?, maxDownloads?, closeDrop }`, `shareDropFilesSchema` étend `createShareSchema` : mêmes limites que `POST /api/shares`, `fileIds` de 1 à `SHARE_FILES_MAX` sans doublon, `closeDrop` obligatoire) : `DropsService.shareFiles` → `FilesService.moveToNewShare` → adapter `moveToNewShare`, **une seule transaction** : verrou sur le dépôt (inconnu, supprimé ou d'un autre type → 404), verrou sur les fichiers (inconnu, d'un autre lien ou supprimé → 404 `FileNotFoundException` ; pas `ready` → 409 `FileNotReadyException`), insertion du lien `share` (slug pris → 409, sans slug l'id généré est retenté `PUBLIC_ID_GENERATION_ATTEMPTS` fois), `UPDATE files SET link_id = <partage>, upload_token_hash = NULL` (les fichiers sont déplacés, pas copiés : pas de place doublée, et le jeton d'envoi du dépôt ne donne plus accès à eux), puis `disabled = true` sur le dépôt si `closeDrop`. Toute erreur annule tout. Réponse : la fiche du partage (`SharesMapper.toDetailResponse`). Audit `shares.created` (avec `fromDropId`) et `drops.files.shared` (`{ shareId, fileIds, closeDrop }`). Un `drop` n'est jamais servi par `/r/`, `/api/links` ni `/api/shares` (404). `GET /api/public/drops/:id` (`drops/public-drops.controller.ts` → `PublicDropsService`, sans session, `@Throttle` `DROP_VIEW_THROTTLE_*`, `Cache-Control: no-store`) rend `id`, `title`, `maxFiles`, `maxTotalBytes`, `filesRemaining`, `bytesRemaining` (reste calculé sur `COUNTED_FILES` via `summarizeCountedLinks`) et `expiresAt`, jamais un fichier reçu ni un expéditeur. Id mal formé (avant SQL), inexistant, désactivé, supprimé ou d'un autre type → même `DropNotFoundException` (404) ; expiré ou plein (`dropState` ≠ `open`, limite `null` comprise) → `DropExpiredException` (410, un seul corps). Un 200 appelle `EventsService.recordView` sans l'attendre.

**Tags** (`tags/`, port `'TagsRepository'`, entité `Tag`) : tables `tags` (`public_id` unique en `utf8mb4_bin` via `generatePublicId()`, `name` d'affichage en `utf8mb4_unicode_ci` sans index unique, `name_key` (nom NFC en minuscules, `toNameKey` de `common/name-key.ts`, partagée avec les dossiers, `utf8mb4_bin`) porteur de l'index unique `UQ_tags_name_key` : unicité insensible à la casse mais sensible aux accents et aux emoji, `name` de 1 à `TAG_NAME_MAX_LENGTH`, sans caractère de contrôle, normalisé NFC et rogné, `color` en `#rrggbb` minuscules, `CHECK` `CHK_tags_color`, `DEFAULT_TAG_COLOR` par défaut) et `link_tags` (clé primaire `(link_id, tag_id)`, FK `FK_link_tags_link` et `FK_link_tags_tag` en `ON DELETE CASCADE`, index sur `tag_id` ; entité `LinkTag`, écrite par les API des liens, des partages et des dépôts, voir « Tags et dossier d'un lien »). API admin `GET/POST /api/tags`, `PATCH/DELETE /api/tags/:id` (`:id` = `public_id`, filtre `TagsExceptionFilter`) : corps validés par `parseDto` (`z.strictObject`, couleur acceptée en majuscules et stockée en minuscules, `PATCH` vide → 400), nom déjà pris → 409 (renommer un tag avec une autre casse de son propre nom reste permis ; une course sur l'index `UQ_tags_name_key` donne aussi 409, une collision d'id généré est retentée `PUBLIC_ID_GENERATION_ATTEMPTS` fois), id inconnu ou mal formé → 404 avant SQL. `linkCount` (liste et réponses de création et de modification) est agrégé en SQL et ne compte pas les liens supprimés (soft delete). Suppression en dur : le `CASCADE` retire les lignes de `link_tags`, les liens ne sont pas touchés. Audit `tags.created`, `tags.updated` (champs modifiés) et `tags.deleted`.

**Dossiers** (`folders/`, port `'FoldersRepository'`, entité `Folder`) : table `folders` (`public_id` unique en `utf8mb4_bin` via `generatePublicId()`, `name` d'affichage en `utf8mb4_unicode_ci`, `name_key` (`toNameKey`, `utf8mb4_bin`, 200 caractères : un nom de `FOLDER_NAME_MAX_LENGTH` peut doubler en minuscules) porteur de l'index unique `UQ_folders_name_key` : unicité insensible à la casse mais sensible aux accents et aux emoji, `name` de 1 à `FOLDER_NAME_MAX_LENGTH`, sans caractère de contrôle, normalisé NFC et rogné ; un dossier n'a que son nom) et colonne `links.folder_id` (nullable, index `IDX_links_folder_id`, FK `FK_links_folder` en `ON DELETE SET NULL` , rangé par les API des liens, des partages et des dépôts, voir « Tags et dossier d'un lien »). API admin `GET/POST /api/folders`, `PATCH/DELETE /api/folders/:id` (`:id` = `public_id`, filtre `FoldersExceptionFilter`) : corps validés par `parseDto` (`z.strictObject({ name })`, `PATCH` sans `name` → 400), nom déjà pris → 409 (renommer un dossier avec une autre casse de son propre nom reste permis ; une course sur `UQ_folders_name_key` donne aussi 409, une collision d'id généré est retentée `PUBLIC_ID_GENERATION_ATTEMPTS` fois), id inconnu ou mal formé → 404 avant SQL. `linkCount` (liste et réponses de création et de modification) est agrégé en SQL et ne compte pas les liens supprimés (soft delete). Suppression en dur : la FK remet `folder_id` à `NULL` sur ses liens, qui ne sont ni supprimés ni modifiés autrement. Audit `folders.created`, `folders.updated` (champs modifiés) et `folders.deleted`.

**Tags et dossier d'un lien** (`links/`, `LinkOrganizationService` exporté par `LinksModule`, qui importe `TagsModule` et `FoldersModule`) : `POST` et `PATCH` de `/api/links`, `/api/shares` et `/api/drops` acceptent `tagIds` (ids publics, 0 à `LINK_TAGS_MAX`, sans doublon) et `folderId` (id public, ou `null` pour sortir du dossier), schémas communs `linkOrganizationShape` de `links/dto/in/link-fields.schema.ts` ; `POST /api/drops/:id/share` les refuse (400). Dans un `PATCH`, `tagIds` remplace toute la liste, absent = inchangé. `resolve` traduit les ids publics en uuid **avant** toute écriture (tag ou dossier inconnu ou mal formé → `TagNotFoundException` / `FolderNotFoundException`, 404 mappés dans les filtres de `links`, `shares` et `drops`, rien ne change) ; les adapters des trois ports (`insert(link, organization)`, `save(link, organization)`) écrivent le lien, suppriment puis réinsèrent les `link_tags` dans **une seule transaction** (`saveWithOrganization`, `links/persistence/link-organization.writer.ts`, qui traduit aussi les violations de FK `FK_link_tags_tag` / `FK_links_folder` par `isForeignKeyViolation`) : une erreur annule tout. Listes et fiches rendent `tags: [{ id, name, color }]` (par nom) et `folder: { id, name } | null` (ids publics seulement), chargés par `loadFor` en deux requêtes pour toute la liste (port `'LinkOrganizationsRepository'`), jamais par ligne ; les réponses publiques (`/api/public/…`) n'en portent pas. L'audit `*.created` ajoute `tagIds` et `folderId` (ids publics), `*.updated` les garde dans `changes`.

**Listes admin** (`GET /api/links`, `/api/shares`, `/api/drops`) : la query est validée par `parseDto` (`z.strictObject`, `listQueryShape` de `common/list-query.ts` plus `state` propre au type : `active` | `disabled` | `expired` pour les redirections et les partages, `DROP_STATES` pour les dépôts) ; paramètre inconnu, répété ou invalide → 400. `q` (1 à `LIST_SEARCH_MAX_LENGTH` après rognage) cherche dans le slug (insensible à la casse), la destination et le titre par `LIKE … ESCAPE '!'` (`toLikePattern` échappe `!`, `%` et `_`) ; `tag` et `folder` sont des ids publics (`folder=none` = sans dossier), un id bien formé mais inconnu donne une liste vide, jamais un 404 ; `sort` ∈ `LINK_LIST_SORTS` (`created_desc` par défaut, `created_asc`, `updated_desc`, `slug_asc`, `slug_desc`, départage par slug) ; `page` de 1 à `LIST_PAGE_MAX` (1 par défaut), `pageSize` de 1 à `LIST_PAGE_SIZE_MAX` (`LIST_PAGE_SIZE_DEFAULT` par défaut). Réponse `{ items, total, page, pageSize }` (`PageResponseDto`) : filtres, tri et compte en SQL par `findLinkPage` (`links/persistence/link-list.query.ts`, seulement des paramètres liés, partagé par les trois adapters `findPage`) ; les clauses d'état suivent `isLinkExpired` (expiré dès `expires_at <= now`), `isLinkUsedUp` (partage expiré ou épuisé) et `dropState` (précédence `disabled` > `expired` > `full` > `open`, nombre et octets comptés selon `COUNTED_FILES`), `now` venant du service. Les résumés (fichiers, tags, dossier, état d'un dépôt) ne sont chargés que pour la page demandée. Aucun index ajouté : `IDX_links_type_created_at`, `IDX_links_folder_id` et la clé de `link_tags` couvrent le tri par défaut et les filtres.

**Envoi public dans un dépôt** (`drops/public-drop-files.controller.ts` → `DropUploadsService` → `FileUploadsService`, sans session, filtre `DropUploadsExceptionFilter`, `Cache-Control: no-store`) : `POST /api/public/drops/:id/files` (`{ name, size, sha256, turnstileToken, uploaderName? }`, `announceDropUploadSchema` = `startUploadSchema` étendu) vérifie Turnstile avec l'IP réelle pour chaque fichier **avant toute lecture** (400 sinon), puis le dépôt (id mal formé, inconnu, désactivé, supprimé → 404 ; `dropState` ≠ `open` → 410), `size` > `FILE_MAX_SIZE_BYTES` → 413, puis `insertWithinLimits`. Réponse : celle de l'admin plus `uploadToken`. `uploadToken` : 32 octets aléatoires en base64url (43 caractères, `common/upload-token.ts`), seul son SHA-256 est stocké (`files.upload_token_hash`), le client l'envoie dans l'en-tête `X-Upload-Token` ; comparaison en temps constant (`timingSafeEqual`), jamais écrit dans un log, l'audit ou une exception. Règle appliquée dans `FileUploadsService.find`, **selon le type du lien** (échec fermé : un fichier de `drop` sans hash n'est jamais servi) ; les partages ignorent le jeton. Mêmes routes que l'upload admin sous `/api/public/drops/:id/files` : `GET /:fileId` (statut), `GET /:fileId/parts`, `PUT /:fileId/parts/:n`, `POST /:fileId/complete`, `DELETE /:fileId` ; jeton absent ou faux, fichier inconnu ou d'un autre dépôt → même 404 (`FileNotFoundException`). Le `DELETE` du visiteur commence par réclamer le fichier par un `UPDATE` conditionnel (`FilesRepository.claimForCancel` : même dépôt, même hash de jeton, non supprimé) qui efface le hash avant tout appel au stockage : un fichier déjà déplacé dans un partage (`POST /api/drops/:id/share`) donne le même 404, et un échec du stockage restaure le hash (`releaseCancelClaim`) pour qu'un nouveau `DELETE` reprenne ; le déplacement vers un partage ne prend de son côté que les fichiers qui portent encore leur hash (un fichier réclamé par une annulation → 404). Dépôt désactivé ou supprimé → 404 sur toutes ces routes ; dépôt expiré ou plein → les envois commencés continuent jusqu'à `complete` (seule l'annonce relit `dropState`).

- **Limites sous verrou** : `insertWithinLimits(file, limitsFor)` reçoit un callback appelé avec le lien verrouillé (`SELECT … FOR UPDATE`) : `dropUploadLimits` (`drops/drop-upload-limits.ts`) y relit l'état (absent, supprimé, désactivé, autre type → `DropNotFoundException` 404 ; expiré → `DropExpiredException` 410 ; limite `null` → refus) et rend `maxFiles`, `maxLinkBytes` (somme SQL `COUNTED_FILES` du lien + taille annoncée, `LinkBytesLimitExceededException`) et le quota global ; deux annonces simultanées ne dépassent donc jamais une limite. Les partages passent `SHARE_UPLOAD_LIMITS` (`maxLinkBytes: null`), inchangés.
- **413 unique** : `DropUploadsService` traduit `TooManyFilesException`, `LinkBytesLimitExceededException` et `StorageQuotaExceededException` (annonce et `complete`) en `DropLimitExceededException` (« Upload exceeds the drop limits »), le filtre fait de même en filet de sécurité : le quota global n'est jamais révélé.
- **Événement et audit** : `EventsService.recordUpload` (type `upload`, migration `AcceptDropUploads`) au `complete` réussi (202), sans attendre. Audit sans `userId` ni IP : `files.created` à l'annonce (`{ dropId, name, size, uploaderName }`), `drops.files.received` au `complete`, `drops.files.cancelled` au `DELETE`.
- **Débit et proxy** : `@Throttle` par IP sur l'annonce (`DROP_UPLOAD_START_THROTTLE_LIMIT`) et les parts (`DROP_UPLOAD_PART_THROTTLE_LIMIT`). `FILE_PART_UPLOAD_PATH_REGEX` (parseur JSON ignoré) et le `location` nginx des parts couvrent `/api/public/drops/:id/files/:fileId/parts/:n` (33 Mo, `proxy_request_buffering off`), le reste de `/api/` garde 1 Mo.
- **Expéditeur** : `files.uploader_name` facultatif (`DROP_UPLOADER_NAME_MAX_LENGTH`, espaces rognés, sans caractère de contrôle ni invisible, vide → `null`), jamais exposé par l'API publique.

**Stockage** : client AWS SDK v3 (`storage/`), `forcePathStyle`, deux clients : interne (`S3_ENDPOINT`) et de signature (`S3_PUBLIC_ENDPOINT`). Bucket privé, accès uniquement par URLs présignées en `Content-Disposition: attachment`. `GET /api/storage/usage` lit `GET /rustfs/admin/v3/quota-stats/<bucket>` signé SigV4 (l'utilisateur de l'app n'a besoin que de `s3:GetBucketQuota`). Le quota RustFS ne suffit pas : avant d'ouvrir un upload, vérifier aussi la place restante côté SQL, et traduire « Bucket quota exceeded » en 413.

## Architecture frontend (`frontend/src`)

Structure plate sous `src/` (pas de `features/`), comme NestWiki : `api/` (un wrapper par domaine, enveloppe `ResponseDto`), `components/` (`ui/` = shadcn généré, **ne pas éditer à la main** ; `layout/` = Topbar/Sidebar/AppLayout), `hooks/`, `lib/` (`api-client.ts` : axios `withCredentials`, 401 → refresh puis rejeu, déconnexion si le refresh échoue), `pages/` (une par route, câblées dans `App.tsx`), `schemas/` (zod), `utils/` (fonctions pures). Imports via `#<dossier>/…`. Après login, `sameOriginPath` (`utils/safe-redirect.ts`) n'autorise qu'une redirection vers le site lui-même. Logos et mascotte repris de NestWiki (`public/logo-{light,dark}.svg`, `public/mascot-{light,dark}.png`).

Page `/redirects` (`pages/Redirects.tsx`, `components/links/`, `hooks/useLinks.ts`) : liste, création, modification, désactivation, suppression (dialogue de confirmation) et copie de l'URL `/r/<slug>`, via `api/links.ts`. `schemas/link.schema.ts` reprend les limites de `links/dto/in/link-fields.schema.ts` (longueurs, alphabet, noms réservés : les garder synchronisés) ; en modification, seuls les champs changés partent dans le `PATCH`. Les statuts 400/404/409 sont traduits par `lib/link-errors.ts` (troisième argument de `extractErrorMessage`). Fiche d'un lien `/redirects/:id` (`pages/RedirectDetail.tsx`, chargée en `lazy` pour sortir recharts du bundle principal) : lien, destination, état et stats (`hooks/useLinkDetail.ts`, graphique `components/links/ClicksChart.tsx` sur le composant shadcn `chart`, listes `TopClicksList`) ; la période vient de `?days=` (`utils/link-stats.ts` : options 7/30/90/365, sinon 30). Les listes de `api/links.ts`, `api/shares.ts` et `api/drops.ts` (`listLinks`, `listShares`, `listDrops`) prennent des `ListParams` facultatifs (`api/list-params.ts`) et rendent une `Page<T>` (`{ items, total, page, pageSize }`) ; `LIST_PAGE_SIZE_MAX` y est à garder synchronisé avec le backend. `useLinks`, `useShares` et `useDrops` parcourent toutes les pages par `fetchAllPages` (`utils/fetch-all-pages.ts`) : les pages d'administration montrent encore tous les éléments, sans recherche ni filtre.

Pages `/shares` et `/shares/:id` (`pages/Shares.tsx`, `pages/ShareDetail.tsx`, `components/shares/`, `hooks/useShares.ts`, `hooks/useShareDetail.ts`, `api/shares.ts`) : même découpage que les redirections, `schemas/share.schema.ts` reprend les limites du backend (`SHARE_MAX_DOWNLOADS_LIMIT`, `FILE_MAX_SIZE_BYTES`, longueur du nom : les garder synchronisés, slug et expiration réutilisent `link.schema.ts`), erreurs traduites par `lib/share-errors.ts` (`shareErrorMessages` pour le partage, `uploadErrorMessage` pour l'envoi). `useShareDetail` relit la fiche toutes les `FILE_STATUS_POLL_MS` tant qu'un fichier est en `verifying`, et à chaque fin d'envoi.

Page `/files` (`pages/Files.tsx`, `components/files/`, `hooks/useFiles.ts`, `api/files.ts`) : fichiers stockés, état, origine (lien vers `/shares/:id` ou `/drops/:id` tant que le partage ou le dépôt existe, `FileOrigin`) et barre de place (`FilesUsage`). Le filtre « Orphelins » vit dans l'URL (`?orphans=true`, toute autre valeur = tous ; `listFiles` n'envoie jamais `orphans=false`, le backend répondrait 400). Erreurs traduites par `lib/file-errors.ts`, une table par route car le 409 change de sens (suppression : encore attaché à un partage ou à un dépôt ; téléchargement : pas prêt). `useFiles` renvoie `reload` (repasse par le chargement) et `refresh` (relit sans squelette, après une suppression) ; une réponse périmée est ignorée. Après une suppression réussie, ou refusée en 404/409 (le fichier a changé ailleurs), la liste est relue et la jauge du Sidebar aussi (`refreshStorageUsage` de `lib/storage-usage-refresh.ts`, écouté par `useStorageUsage`). Le bouton supprimer d'un fichier `inUse` est désactivé, avec l'infobulle `title` sur son `span`.

Page `/drops` (`pages/Drops.tsx`, `components/drops/`, `hooks/useDrops.ts`, `api/drops.ts`) : liste, création, modification, désactivation, suppression (le `ConfirmDeleteDialog` des partages) et copie de l'URL complète `/u/<slug>` ; le titre mène à la fiche `/drops/:id` (`pages/DropDetail.tsx`, `hooks/useDropDetail.ts` qui relit toutes les `FILE_STATUS_POLL_MS` tant qu'un fichier est en `verifying`, `components/drops/DropFilesTable.tsx`) : réglages, vues, fichiers reçus avec état et expéditeur (`uploaderName` affiché en texte brut uniquement : il vient d'un visiteur anonyme), téléchargement direct (`createFileDownloadUrl`) et suppression après confirmation (`dropFileDeleteErrorMessages`) ; l'état (`open`, `full`, `expired`, `disabled`) vient de l'API (`DropStateBadge`). **Envoi de fichiers** : `UploadQueueProvider` (`components/`, sans dépendance à la session, à l'API ni au routeur : il reçoit `targetOf`, qui donne la cible d'envoi d'un `shareId`, clé de regroupement de la file) porte une `UploadQueue` (`lib/upload-queue.ts`, lue par `useUploads(shareId)` via `useSyncExternalStore`) : un fichier à la fois, `revision` monte à chaque fin d'envoi ; `beforeunload` tant qu'un envoi tourne. `UploadsProvider` (monté dans `AppLayout`, l'envoi survit à un changement de page, tout est arrêté sans rien supprimer à la déconnexion) l'instancie avec `shareUploadTarget` (`lib/share-upload-target.ts`, appels de `api/shares.ts`). Ni `lib/share-upload.ts` ni `lib/upload-queue.ts` n'importent `#api/shares` : ils passent par une `UploadTarget` (`lib/upload-target.ts` : `announce`, `listParts`, `sendPart`, `complete`, `cancel`). La cible peut porter une donnée propre à chaque fichier, `uploadToken` (renvoyé par `announce`, rejoué dans le `UploadHandle` de chaque appel suivant, mémorisé dans `utils/pending-uploads.ts` pour la reprise et pour l'annulation d'une reprise), et un `beforeAnnounce(signal)` facultatif, attendu juste avant l'annonce (après l'empreinte) dont le résultat est passé à `announce` ; un abandon pendant cette attente annule l'envoi sans annoncer. `lib/share-upload.ts` déroule `uploadNewFile` et `resumeFile` : empreinte (`lib/file-hash.ts` → `lib/sha256.worker.ts` → `utils/file-sha256.ts` : `@noble/hashes`, pur JS car la CSP refuse le wasm, tranches `File.slice` de `SHA256_CHUNK_BYTES`, jamais le fichier entier ; le worker est un chunk same-origin de `/assets/`, donc `script-src 'self'` suffit, ne pas passer en worker `blob:`), annonce, parts par `file.slice` (`utils/file-parts.ts`, `PART_CONCURRENCY` en parallèle), relance d'une part seule sur erreur réseau, 408, 429 (`Retry-After`) ou 5xx, `PART_MAX_ATTEMPTS` essais au plus, puis `complete`. Annuler = `DELETE` du fichier s'il est déjà ouvert côté serveur, y compris pour une reprise (un 404 sur ce `DELETE` vaut succès : ligne retirée, entrée oubliée). Le slug d'un partage est verrouillé pendant un envoi (les parts le visent). **Reprise** : `utils/pending-uploads.ts` garde dans `localStorage` les métadonnées de chaque envoi ouvert, jamais le contenu (clé `fileId`, entrées oubliées quand le fichier n'est plus `uploading` et n'a plus de ligne dans la file, échec compris : la fiche ne connaît pas encore un fichier ouvert depuis son dernier chargement) ; avec une entrée, le fichier re-sélectionné doit avoir mêmes nom, taille et `lastModified`, et le hash mémorisé évite de le recalculer ; sans entrée, même taille puis SHA-256 recalculé égal à celui renvoyé par `GET …/parts`, sinon `DifferentFileError`, sans rien envoyer ; seules les parts absentes ou de mauvaise taille repartent (`missingParts`).

**Page publique `/u/:id`** : route SPA (`pages/DropUpload.tsx`, hors layout admin) qui lit `GET /api/public/drops/:id` (`hooks/usePublicDrop.ts` : `loading`, `ready`, `notFound` → `NotFound`, `closed` (410) → `DropClosed`, `failed` avec le délai du 429 et un bouton « Réessayer » ; `refresh` relit sans squelette, un 410 à ce moment marque le dépôt fermé sans quitter la page) et purge `purgeExpiredUploads()` au chargement. Aucun appel ne passe par la session : `api/public-drops.ts` utilise `lib/public-api-client.ts` (axios **sans** intercepteur, donc un 401 ne déclenche jamais le refresh d'`api-client`). Le dépôt est envoyé par la même file que l'admin : `UploadQueueProvider` (prop `onUploaded`) reçoit `dropUploadTarget` (`lib/drop-upload-target.ts`) dont `beforeAnnounce` attend `TurnstileGate.next` (`lib/turnstile-gate.ts` : un jeton par fichier, demandé après l'empreinte, effacé à l'usage ; `onConsumed` réinitialise le widget ; sans `VITE_TURNSTILE_SITE_KEY`, jeton vide immédiat) et dont `announce` envoie le nom de l'expéditeur (`DROP_UPLOADER_NAME_MAX_LENGTH`) ; le jeton d'envoi (`X-Upload-Token`) voyage dans le `UploadHandle`. Les refus locaux (trop gros, place restante dépassée, dépôt fermé ; seuls les envois annoncés depuis le dernier chargement de l'aperçu, ou pas encore annoncés, sont retranchés : un envoi repris est déjà compté par le serveur) passent par `utils/drop-capacity.ts` avant toute empreinte, les envois interrompus (`pendingUploadsOf`) se reprennent ou s'abandonnent, et `useDropReceipts` suit les fichiers envoyés (`getDropFile` toutes les `FILE_STATUS_POLL_MS` tant qu'un est en `verifying` ; un 404 le marque `unavailable`, une erreur passagère le laisse en `verifying`). Messages d'erreur : `dropUploadErrorMessage` (`lib/drop-errors.ts`). **Jeton d'envoi** : la file le garde en mémoire (`Map` par `fileId`) pour reprendre dans la même session même si `localStorage` refuse l'écriture ; dans `pending-uploads`, une entrée avec jeton porte `savedAt` et expire après `PENDING_UPLOAD_TOKEN_TTL_MS` (7 jours, une entrée sans `savedAt` est expirée), elle est oubliée à la fin de l'envoi (prêt, rejeté, annulé). `item.error` ne garde jamais l'erreur axios (`config`, en-têtes, jeton) : `toUploadError` (`lib/upload-error.ts`) la réduit à une `UploadRequestError` (statut, message du serveur, `Retry-After`), que `extractErrorMessage` comprend comme une erreur axios.

## Langue (i18n)

Comme NestWiki : l'interface est en français ou en anglais, au choix de l'admin, pour tout le site (pages publiques `/d/` et `/u/` comprises). ## Règles transverses du plan

- Redirections en **302** uniquement (destination modifiable), jamais 301.
- Même 404 pour un lien inexistant, désactivé ou supprimé ; 410 + page « lien expiré » pour un lien expiré.
- Destinations en `http`/`https` uniquement, longueur max ; slugs limités à un alphabet, hors noms réservés.
- Uploads multipart du navigateur vers le backend, qui les transmet en flux à S3, parts < 100 Mo (limite du Cloudflare Tunnel) ; taille et SHA-256 vérifiés en fin d'upload, MIME détecté côté serveur, refus pendant l'envoi (413).
- Opérations multi-étapes en transaction ; contraintes en base (FK, unicité des IDs publics, `NOT NULL`).
- Tout est modifiable après création (destination, limites, expiration).
